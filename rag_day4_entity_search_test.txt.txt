RAG API Day 4 实体检索与混合召回测试说明

本文件用于验证 Day 4 的 entity search 和 hybrid retrieval。系统已经在 Day 3 完成实体抽取，上传文档后会把实体写入 RAG_ENTITIES，把 document、chunk 和 entity 的关联写入 RAG_DOCUMENT_ENTITY_LINKS。Day 4 的目标是在 keyword search 之外增加 entity search：先根据用户问题抽取查询实体，再查 RAG_ENTITIES，之后通过 RAG_DOCUMENT_ENTITY_LINKS 反查 RAG_DOCUMENT_CHUNKS 中的相关 chunk。

一、PDF 导入依赖什么库

/upload 接口负责文档导入。用户上传 PDF 文件时，系统会读取文件内容并保存到 RAG_DOCUMENTS 表，然后把文本切分成多个 chunk 写入 RAG_DOCUMENT_CHUNKS 表。PDF 导入和解析依赖 PDFBox 库，PDFBox 是当前项目中处理 PDF 文档内容提取的核心 library。对于 txt 文件，系统可以直接读取文本内容；对于 pdf 文件，系统需要通过 PDFBox 提取页面文本。

因此，当用户询问“PDF 导入依赖什么库”时，系统应该通过实体检索命中 PDF、PDFBox、/upload、library、导入、上传等实体，并召回包含 PDFBox 和 /upload 的 chunk。这个问题的理想回答是：PDF 导入依赖 PDFBox，上传入口是 /upload，解析后的内容会保存为文档和 chunk。

二、embeddingStatus 属于哪张表

RAG_DOCUMENT_CHUNKS 表用于保存文档切分后的分块内容。每条 chunk 记录通常包含 ID、DOCUMENT_ID、CHUNK_INDEX、CONTENT、TOKEN_COUNT、CREATE_TIME 和 EMBEDDING_STATUS 等字段。在 Java 代码或接口响应中，EMBEDDING_STATUS 可能会映射为 embeddingStatus。embeddingStatus 表示当前 chunk 的向量化或后续处理状态。

常见状态包括 PENDING、DONE、FAILED、ERROR 和 EMBEDDING_DONE。PENDING 表示 chunk 还在等待处理，DONE 或 EMBEDDING_DONE 表示处理完成，FAILED 或 ERROR 表示处理失败。因此，当用户询问“embeddingStatus 属于哪张表”时，系统应该召回 RAG_DOCUMENT_CHUNKS 表相关 chunk，并说明 embeddingStatus 对应数据库字段 EMBEDDING_STATUS，属于 RAG_DOCUMENT_CHUNKS。

三、chunk 大小在哪里定义

当前项目的 chunk 切分逻辑在 DocumentChunkService 中实现。DocumentChunkService 负责把文档文本切成多个 DocumentChunk，并调用 saveChunks(...) 保存到 RAG_DOCUMENT_CHUNKS。chunk 大小由 CHUNK_SIZE 常量控制，例如 private static final int CHUNK_SIZE = 500。这个值表示每个 chunk 最多截取约 500 个字符。每个 chunk 的 tokenCount 当前可以简单使用 content.length() 计算，并写入 TOKEN_COUNT 字段。

因此，当用户询问“chunk 大小在哪里定义”时，系统应该通过实体检索命中 chunk、CHUNK_SIZE、DocumentChunkService、saveChunks(...)、TOKEN_COUNT、chunkIndex、chunkContent 等实体，并召回包含 DocumentChunkService 和 CHUNK_SIZE 的 chunk。这个问题的理想回答是：chunk 大小定义在 DocumentChunkService 的 CHUNK_SIZE 常量中，保存时会生成 chunkIndex、content 和 tokenCount。

四、SearchService 的 entity search 流程

Day 4 扩展 SearchService，新增 searchByEntity(String keywordOrQuestion) 和 searchHybrid(String question)。searchByEntity 会先调用 QueryEntityExtractionService，从用户问题中抽取 QueryEntity，例如 PDF、PDFBox、embeddingStatus、RAG_DOCUMENT_CHUNKS、chunk、CHUNK_SIZE、DocumentChunkService 等。每个 QueryEntity 会包含 text、normalizedText、entityType 和 weight。

实体检索的核心流程是：question -> query entities -> RAG_ENTITIES -> RAG_DOCUMENT_ENTITY_LINKS -> RAG_DOCUMENT_CHUNKS。系统先根据 normalizedText 查询 RAG_ENTITIES.NORMALIZED_NAME，再根据 ENTITY_ID 查询 RAG_DOCUMENT_ENTITY_LINKS，最后根据 CHUNK_ID 反查 RAG_DOCUMENT_CHUNKS.CONTENT。

五、hybrid retrieval 合并规则

searchHybrid(String question) 会同时执行 keyword search 和 entity search。keyword search 负责根据关键词直接检索 RAG_DOCUMENT_CHUNKS.CONTENT；entity search 负责根据实体链路反查 chunk。两类结果会被合并为 mergedChunks。

第一版 hybrid 排序规则如下：
1. 同时命中 keyword 和 entity 的 chunk 优先。
2. entity 命中数量更多的 chunk 优先。
3. chunkIndex 更小的 chunk 优先。
4. documentId 更新的 chunk 优先。

例如，“PDF 导入依赖什么库”可能通过 keyword 命中 PDF，也可能通过 entity 命中 PDFBox、/upload 和 library。hybrid retrieval 应该优先返回同时包含 PDF 和 PDFBox 的 chunk。又例如，“embeddingStatus 属于哪张表”应该优先返回同时命中 embeddingStatus 和 RAG_DOCUMENT_CHUNKS 的 chunk。

六、关键服务和类

SearchService 负责统一检索能力，包含 searchByKeyword、searchByEntity 和 searchHybrid。QueryEntityExtractionService 负责从用户问题中抽取查询实体。EntityExtractionService 负责 ingestion 阶段从 chunk 文本中抽取实体。ContextBuilderService 负责把检索结果整理成 structuredContext。AnswerBuilderService 负责根据上下文生成 answer。

常见 DTO 和类包括 QueryEntity、EntitySearchHit、HybridSearchResult、ChunkHit、SearchResult 和 AskContext。QueryEntity 保存问题侧实体。EntitySearchHit 保存实体检索命中的 chunk。HybridSearchResult 保存 keywordHits、entityHits、mergedChunks、queryEntities 和 retrievalMode。

七、关键数据库表和字段

RAG_ENTITIES 保存实体主数据，字段包括 ID、ENTITY_NAME、ENTITY_TYPE、NORMALIZED_NAME 和 CREATED_AT。RAG_DOCUMENT_ENTITY_LINKS 保存 document、chunk 和 entity 的关联，字段包括 ID、DOCUMENT_ID、CHUNK_ID、ENTITY_ID、SOURCE_TEXT 和 CREATED_AT。RAG_DOCUMENT_CHUNKS 保存文本分块，字段包括 ID、DOCUMENT_ID、CHUNK_INDEX、CONTENT、TOKEN_COUNT、CREATE_TIME 和 EMBEDDING_STATUS。

当系统查找 PDFBox 时，可以在 RAG_ENTITIES 中找到 normalizedName 为 pdfbox 的实体，再通过 RAG_DOCUMENT_ENTITY_LINKS 找到相关 CHUNK_ID，最终回到 RAG_DOCUMENT_CHUNKS 读取 CONTENT。查找 embeddingStatus 时，可以找到 normalizedName 为 embeddingstatus 的实体，并召回包含 RAG_DOCUMENT_CHUNKS 和 EMBEDDING_STATUS 的 chunk。查找 chunk 大小时，可以通过 chunk、CHUNK_SIZE、TOKEN_COUNT 和 DocumentChunkService 等实体召回对应 chunk。

八、验收问题与预期召回

验收问题一：PDF 导入依赖什么库
预期命中实体：PDF、PDFBox、/upload、library、导入、上传
预期召回内容：PDF 导入依赖 PDFBox，/upload 接收文件，解析后保存文档和 chunk。

验收问题二：embeddingStatus 属于哪张表
预期命中实体：embeddingStatus、EMBEDDING_STATUS、RAG_DOCUMENT_CHUNKS、FIELD、TABLE
预期召回内容：embeddingStatus 对应 EMBEDDING_STATUS 字段，属于 RAG_DOCUMENT_CHUNKS 表。

验收问题三：chunk 大小在哪里定义
预期命中实体：chunk、CHUNK_SIZE、DocumentChunkService、saveChunks(...)、TOKEN_COUNT、chunkIndex、chunkContent
预期召回内容：chunk 大小由 DocumentChunkService 中的 CHUNK_SIZE 常量定义，例如 CHUNK_SIZE = 500。

九、路径、配置和库

上传文件默认路径可以是 D:/rag_api/uploads/。代码路径示例包括 src/main/java/com/example/rag/service/ 和 src/main/java/com/example/rag/service/impl/。项目使用 Spring Boot 和 Oracle。PDF 解析使用 PDFBox。配置文件包括 application.yml 和 application.properties，常见配置项包括 spring.datasource.url 和 server.port。

十、最终验收说明

上传本文件后，Day 3 的实体抽取流程应该能抽取 API、TABLE、FIELD、CONFIG、SERVICE、CLASS、METHOD、STATUS、LIBRARY 和 PATH 等实体。Day 4 的 entity search 应该能通过这些实体反查 chunk。Day 4 的 searchHybrid 应该能把 keyword hits 和 entity hits 合并为 mergedChunks，并为 /ask 提供更稳定的上下文。
